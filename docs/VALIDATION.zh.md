# 验证范围与已知限制

## 证据如何解读

| 类别 | 已有证据 | 不能据此推断 |
|---|---|---|
| 现场人工反馈 | 遥控器普通行走、网页速度对照在指定速度下确实产生行走 | 所有固件、姿态、速度和目标都通用 |
| 办公室调试 | 实际部署中多次定位、转向、导航与障碍问题的处理 | 系统已经通过完整可靠性验收 |
| 中央目标修复 | 中文解析、正确目标、真实数据路线预览和旧计划清理检查 | 已完成一次中央目标现场到达验收 |
| 离线回归 | 模拟控制、定位状态、障碍层、转向反馈、停止、解析与 UI 状态测试 | 物理动力学、实际碰撞距离或厂商步态效果 |
| 连续只读观察 | 最新一轮 180 个一秒采样中 177 个定位在线，最长连续非在线 2 个采样；12 次中央预览中 11 次成功 | 定位永不中断；此样本也不是全场景成功率 |
| 机器人端源码 | 提供遥操作集成参考和官方手势适配代码 | 已核对当前机器人所有运行文件；此次导出时机器人无法连接 |

仓库不包含含私人运行信息的原始诊断录包或任务日志。现场反馈与上述观察属于既有项目证据，发布校验中的测试结果另见 [RELEASE_CHECKS.md](../RELEASE_CHECKS.md)。

## 离线检查

```bash
python -B scripts/check-release.py
python -B scripts/test-office.py
```

第一项检查 Python 语法、文本 CR 字节、敏感模式、交付文件和命名地图点。第二项运行硬件无关回归以及 AMCL 纯几何测试，使用模拟客户端和临时数据，不订阅真机或启动运动服务。

上游框架测试位于 `tests/`，需完整 HomeBody 依赖；与办公室轻量回归分开。传感器 C++ 编译和容器构建也独立于 Python 测试，不应将它们混写为“测试全部通过”。

## 定位为何仍可能暂停

AMCL 的输出不仅取决于粒子方差，还要通过当前二维切片与三维点云核验。相似墙面、家具改变、遮挡、雷达运动、无线积压或会话重置都可能造成候选暂时不被接受。

已实现：当前几何验证支持下的短时跟踪、靠近已验证变换的滞回、自动三维初始化、同会话受限等待和原目标重规划。AMCL 随机恢复注入参数与参考项目一致为零，持续失配仍通过显式全局定位和独立三维种子恢复。

没有实现：断网后凭空输出新坐标、跨会话复用旧变换、忽略大幅跳变或在定位失效时继续盲走。

## 实际运动限制

- 当前行走 **0.35 m/s**、转向上限 **0.45 rad/s** 来自本项目调试配置，实际步态响应由 G1 固件和控制状态决定。
- 官方接口返回成功不等于物理动作完成。任务完成需要观察到反馈；无法确认位移或转角时会说明原因。
- 转身会有底座平移，闭环允许有限误差并处理有证据支持的地图修正；超过可解释范围仍停止。
- 低矮障碍、透明物体、反射面、地图外障碍和人群不能仅靠当前高度切片完整表达。
- 模型推算的雷达到底座变换仍需按设备安装情况核对，不能当成现场测量标定。
- 官方手势可能受设备能力、控制状态和 SDK 版本影响；仓库含适配与测试，不宣称所有硬件版本均已验证。

## 发布副本与当前部署

发布副本将主机路径和地址改为环境配置，并整理了目录、依赖和部署入口。已有控制逻辑、阈值和运动护栏没有为发布而放宽。当前机器人和工作站的既有运行文件保持只读。

首次发布未在另一台干净机器人上完成全流程验收；未重新完成完整传感器镜像构建。先做离线检查，再按部署文档逐层核对接口，不要把一个 Git clone 当成机器人已经就绪。
